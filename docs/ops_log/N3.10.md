Unit N3.10 (NEXT_PHASES_PLAN_2026_10.md, Phase N3). The admin "onboard dealer" POST on
`/admin/dealers` now returns 409 with "Onboarding is paused; use dealer-discovery (see
P15A.3)" and calls nothing in the job queue. No worker has consumed `dealer_jobs` since the
worker and scheduler services were deleted on 2026-10-08 (SCANNING_OPS_LOG.md:1264, which also
records that prod `dealer_jobs` was empty at every check that day). No jobs were deleted.

## 2026-10-18, N3.10b: the other web paths that queued `dealer_jobs`

The N3 integrator found three more web entry points that still inserted rows. Owner decision
D-IF3 = (a) (2026-10-18) pauses them the same way. For a site admin each answers 409 with
`{"ok": false, "error": "onboarding_paused", "message": "Onboarding is paused; use
dealer-discovery (see P15A.3)"}` before rate limiting, validation or diagnosis, and calls
nothing in the job queue:

| Endpoint | UI control | Before N3.10b |
|---|---|---|
| `POST /api/admin/dealer-onboard` | Find dealers "Request scrape" | `request_dealer_onboard` -> `enqueue_job` |
| `POST /api/admin/dealer-jobs/<id>/retry` | hub "Restart" / "Restart job" | `retry_failed_job` -> `enqueue_job` |
| `POST /api/admin/dealer-jobs/<id>/smart-retry` | hub "Smart restart" | `smart_retry_failed_job` -> `enqueue_job` |

Find dealers no longer draws "Request scrape"; site admins see the paused line in its header.
The hub draws no Restart buttons. The flag is `QUEUE_ONBOARDING_PAUSED` in
`backend/dealer/admin/onboarding_paused.py`, a constant (not an env knob). No queue code was
deleted (P15A.3 owns removal). Non-admins still get 403, and a POST without the CSRF header
still gets 403.

Not changed, because they never touch `dealer_jobs`: `POST /api/admin/dealer-jobs/<id>/diagnose`
(updates `result_json` on an existing row), the `/dev` and `/api/admin/operator` smart-import
(runs the dealer pipeline in-process), and `POST /admin/dealers/<id>/rescan` (spawns the scanner
in-process; off unless `ALLOW_STORE_ADMIN_RESCAN=1`). `schedule_due_refresh_jobs` is called only
by `scripts/scanner_scheduler_loop.py`, not by the web app.

Row-count check on a throwaway local database (`pytest_n310b`, created and dropped for this
check; `cars` and `cars_cleanroom` were not touched): with one failed onboard row seeded, the
three endpoints plus the N3.10 hub POST answered 409 each and `dealer_jobs` stayed at 1 row.
The same run against the pre-N3.10b `admin_dealer_api.py` answered 200 (onboard), 200 (retry)
and 400 (smart-retry, `already_active` after the retry) and left 3 rows.
