## 1. What discovery keeps from `scrape_inventory_path`

`discovery_capture.capture_endpoints` (discovery_capture.py:124-130) is the only caller (`git grep` finds no other). It takes the five-tuple and uses it like this:

| Output | Use in discovery | Where |
|---|---|---|
| `records` (intercept bodies, plus the synthetic `*_inventory` rows the platform branches append) | Length only, added to `out["records"]`. That number is logged in discovery.md and passed through `runner.run_discovery_capture` / `lifecycle`. No decision reads it. | discovery_capture.py:129; runner.py:82; lifecycle.py:236 |
| `html` (page content) | Discarded | :124 |
| `url_denied` | One log line | :131-132 |
| `card_locations` | Discarded (`_card_locs`) | :124 |
| `captured_endpoints` = `observer.ledger.endpoints` | Deduped across paths by `(method, url without query)` (:147-161), then `promote_from_ledger(validate=True)` turns them into recipes | :130, :163-178 |

The ledger is the only output that turns into anything, so a branch matters to discovery only if it changes the ledger. These ledger rules decide that (network_observer.py):

- Only `page.on("response")` events of the page the observer is attached to are seen (:568). The observer never sees HTTP done in Python (`requests`, `aiohttp`), and never sees a page in a different browser context.
- The response must be JSON by content-type, or an `xhr`/`fetch` response whose body sniffs as JSON or as an HTML fragment with at least 5 VINs (:609-666, :689-734). Document navigations (server-rendered SRP pages) are never ledgered.
- The endpoint key is `(method, host, path)` (:387-389). The first response for a key fixes the URL, query, POST body and auth headers. Later responses for the same key only add `occurrences`, raise `vehicle_rows` and the `field_coverage` fractions to their maximum, and fill a missing `total_count` (:448-463).

An in-page `fetch()` issued through `page.evaluate` is an ordinary page request and does fire the response event. The dealer.com evidence in section 3 confirms this: those bodies can only have come from that path.

## 2. Classification

Ledger reach: **direct** means the branch's own requests become ledger endpoints. **indirect** means it makes the page fire requests that become endpoints. **none** means its output is rows or state that discovery discards. ## 5. Incidental findings (outside the branch list; flagged for owners)

1. **discovery_capture drops dealer.com and CarsCommerce sections.** The cross-path dedupe at discovery_capture.py:147-161 keys on `(method, url without query)`. In the ledgers, 97 of 102 dealer.com runs carry a different `pageAlias` / `listing.config.id` per path (new, used, certified) at the same `getInventory` URL. Discovery therefore promotes only the first path's section. The browser-era `dealer_run` passed all path endpoints to `promote_from_ledger`, whose recipe key separates sections (recipes.py:109-117). Fix: dedupe on `EndpointRecipe.key()` semantics, or on `(method, url, post body)`. This belongs with P17B.11 or a recipe-store phase, not a deletion unit.
2. **Early-return detectors fire on other platforms.** `_is_shopperexpress_html` matched holmanhondacentennial-com (CarsCommerce), and `_is_autowall_html` matched centralhoustonnissan-com (dealer.com ledgers). The early return skips the generic pagination. After slimming, the autoWALL return is cheap. The ShopperExpress navigation should run only when profile/fingerprint confidence agrees, or after the generic loop instead of in place of it.
3. **The facet-scoped `getInventoryAndFacets` recipes** (pageSize 8-28; P0B.1's "facet-filtered fragment" shape) are the page's own request. Without the bulk POST they would be the only dealer.com capture, which is why 1b is kept.
4. **kiaofcleveland-com's two recipes** are labelled `provider_hint: dealer_dot_com` because discovery's default provider was dealer_dot_com. P0B.1 can check whether they replay the full lot (`pagination: none`, 50 rows each).

## 6. What this means for D-DC5

None of these branches runs in a scan. They live only in discovery's browser capture, which D-DC5 keeps. Slimming as specified takes out of each capture: about 200 lines of nav, the 150-line card-location module, two full-lot VDP crawls per path (autoWALL, ShopperExpress) and up to 50 extra in-page POSTs per dealer.com path. It changes no ledger key that has ever produced a recipe. It gives P17B.5 two constraints. Keep a navigation-only ShopperExpress helper. Keep inventory_scrape's own PixelMotion click loop; that is separate from `scrapers/pixel_motion.py`'s page scraper, which P17B.5 deletes.
