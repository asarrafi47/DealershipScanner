## 1. The honest answer to "why is the site slow"

On a fast laptop with a warm origin it is not slow: 0.4-0.7 s per page (1.4 s for a listings page that searches by itself) and 0.5-0.6 s per search. On a phone (iPhone 14 viewport, 9 Mbps, 150 ms RTT, 4x CPU) it is 0.9-1.5 s per page and 2.7-4.2 s for anything with results. On any device the first request after a quiet spell can take 2-5 s. Reading it:
- Rank 4 is the longest wait but the rarest; live-speed.md says the stalls are what make the site feel broken, ranks 1-3 are what make it feel slow every time. On a low-traffic site the stall may be the usual case.
- The staged releases fix none of the five (server-causes 11, live-speed 8) and make the deploy-time cold start worse: `CARD_REV` changes three times (1.5.11, 1.5.12, 1.5.16), so every stored card is stale after deploy until `python -m backend.scripts.build_listings_grid_cards` runs (150-171 s on Railway; `docs/RELEASING.md` does not mention it), and N37a adds one more Postgres connection per car page.
- Redis fixes the first-search miss (as a store) and the worker-memory problem; it does not make a phone page faster (live-speed 6, redis.md 1).

## 2. How good the search bar is

**Score: 145 / 240 = 60%** (parse 73/120 = 61%, relevance 72/120 = 60%; 60 queries x 2 x 2). The earlier pass scored 146/240 = 61%; the two differ on one query (D4, a deliberate override). Third pass reproduced the live parse of 66/66 queries, result counts 34/34 and top-5 car ids 34/34 [C]. 27 of 60 queries are fully right, 17 are wrong on both counts. 16 of 60 return no cars live; 2 of those (nonsense) are correct, 13 of the other 14 have 8-8,629 matching cars in the area. Replaying the staged tip's parser projects 149/240 = 62% (only `bmw i4` changes) [C]. The scores are judgement under a stated rubric [U]; the counts are not.

**What works** (category share of points): condition 92%, feature 80%, misspelling 75%, body style 75%, fuel 75%, colour 75%, nonsense 100%. Examples that work: `toyta camry`, `hundai tucson`, `porshe cayenne` (make typo absorbed), `honda civic under 20k`, `under $25,000`, `2020 or newer tacoma`, `2018-2021 4runner`, `used bmw`, `white rav4`, `red mustang`, `mercedes gle 350`, `plug-in hybrid suv`, a pasted VIN. Of the 40 most listed models, 34 parse cleanly (79.7% of their cars). It is a good keyword-to-filter translator for one grammar and a poor search engine for everything else; the pgvector layer does not take part in production search (behavioural evidence; the env vars could not be read [U]). Weak: natural language 20%, the site's own examples 0% (6 of 7 return no cars, the 7th returns other models), drivetrain 38%, ranges 50%, make/model/trim 57%.

## 3. Search promotion

## 5. Redis

**Position.** Production has no Redis (`/api/ready` says `redis: skipped`); the one worker is intentional (C3). Redis buys little at one worker and a lot at two or more; it never makes a phone page faster. Do R0 (no Redis) now; treat R1-R4 as optional until a second worker is wanted.

**What moves (R1-R3, optional)** and what it buys [C unless tagged; local numbers, no Redis server was ever run, stand-in = shared directory + fakeredis]:

| Moves | Gain |
|---|---|
| Listings scope bodies (gzip-6 mtime 0 + brotli-5, hash with etag) behind a 32 MB in-process L1; partial and hidden-dealer bodies stay in L1 | Body another worker built: 774 ms -> 3.3 ms; first 8 `/listings` after a restart 2,387 -> 194 ms (only if token and `CARD_REV` are unchanged); 20 metros 1,088 ms median / 31.3 s total -> 7.6 ms / 0.6 s; builds for the same traffic 28-30 -> 21 |
| Facets keyed by the write fingerprint alone (219 KB json_gz + 74 KB api_gz + 725 KB packed) and a shared 60 s grid token | First `/listings` 2.8-3.2 s -> 93-95 ms; survives `CARD_REV` deploys and the day roll |
| Rate limiter, login lockout, AI budgets (Lua sliding window, hashed keys) | Exact limits across workers (5 allowed of 8 attempts over 2 workers); survive a deploy |
| Narrations 30 d, Places 6 h, cohorts 900 s, query vocabulary (day key), parse cache 24 h, per-area examples 1 h, dealer cards 1 h, billing 60 s | Billable calls survive a deploy; vocabulary build 1.86 s and +110 MB stops repeating per worker |
| Fleet aggregates (rarity, plausibility, bands, featured cars, count, fallback URLs): **Postgres row first**, Redis an optional copy | A Redis TTL refilled on a request keeps the stall; the cure is compute off the request (P6) |

**What stays.** In process: the 65 `lru_cache` static lookups (EPA, trim ladders, specs; sub-microsecond, thousands of hits per page), `_VPIC_MEMO` (bound it at 50k entries). Postgres: card store `listings_grid_cards` (530 MB), vPIC cache (912 MB), job queue, `/dev` job store (move to Postgres), users. Signed cookie: Flask session (server-side sessions would add a Redis hit to every request). Never: the legacy whole-fleet grid (dead code), pickle values.

**Expected gains, measured locally** (macOS, Python 3.14, load average 8-12):

| | Today | With the store | With streaming assembly too |
|---|---|---|---|
| 2 workers, sum of per-worker peak RSS | 3,145 MB (1 worker: 2,199 MB) | 2,898 MB (-8%; seeds -19% / +4%) | **2,410 MB (-23%)** |
| Car pages per second, 8 clients, 1 / 2 / 4 workers | 30.2 / 52.4 / 62.5 (p95 332 / 253 / 235 ms) | 2 workers 57.2, p95 221 ms | same |
| Body bytes, 20 scopes | 56.1 MB gzip | **28.7 MB brotli-5 (-48.8%)**; 28105 r50 download on Slow 4G 6,480 -> 3,744 ms, Fast 4G 1,255 -> 766 ms | same |
| Rebuild with unchanged content | new ETag -> 200 + 1.59 MB | same ETag -> 304 | same |

The "-73% memory" of the first draft was a worker that never builds; it was withdrawn (section 8). A second worker costs about 10-13% more than the single worker today only with store + streaming assembly (3.12). Redis makes a second worker correct and cheaper, not faster. Memory price estimate: about +0.33 GB ($3/month) per extra worker with R0+R1, +1.4 GB today [U, ratios from macOS].

**Rollout order.** R0 (no Redis; helps the single worker): `gzip.compress(..., mtime=0)` and an ETag from the raw-body digest (P5); the five aggregates off the request path with stale-while-revalidate (P6); streaming assembly of the scope body with `zlib.compressobj` and in-process stale-while-revalidate across a token change and the UTC day roll (P19); `backend/cache/shared.py` (client, breaker, codecs) unused until R1. Then R1 shared token, bodies, facets, claims (flags `REDIS_LISTINGS=1`, `LISTINGS_BR=1`); R2 rate limiter (`RATE_LIMIT_BACKEND=redis`, falls back to memory); R3 narrations, Places, cohorts, vocabulary, parse cache, examples, dealer cards, billing; R4 a `warmer` producer outside the web workers (`LISTINGS_WARM=1`, the only way the worker stays near 0.3 GB); then `GUNICORN_WORKERS=2`; 3-4 workers only with the Postgres pool of P14 (the plateau at 4 workers is connection cost, not Redis).

**When Redis is down it must never be an error.** Client created lazily after fork: `socket_connect_timeout=0.1`, `socket_timeout=0.5`, `max_connections=8`, and **`retry=Retry(NoBackoff(), 0)` is required**: redis-py's default retry policy took 3.2-5.7 s per failure against a hung listener or closed port; with it a failure costs 50-250 ms. Circuit breaker: any `RedisError`/`OSError` opens it for 30 s, an open call costs 0.095 microseconds, then one probe. Tested shapes (fakeredis and failing sockets, 8 shapes: hung listener, unroutable address, unresolvable name, refused port, reset mid-reply, `-LOADING`, `-OOM`, garbage): the built body is returned every time, the first failure costs at most 0.5 s, later calls 0.004 ms [C against stand-ins; no real Redis server was run, so private-network latency and eviction are [U]]. Fallbacks equal today's behaviour: build in process, in-process limiter, call the provider, per-process billing cache. `/api/ready` keeps Redis optional and adds `redis_breaker` and hit/miss/error/fallback counters. Redis restart = empty cache (safe); values over 16 MB are refused.

**Railway.** One service in project `dealership-scanner`, environment `production`, same region as web (the ops-log snapshot says `us-west2` [U]), private network only (delete the template's TCP proxy; never put `REDIS_PUBLIC_URL` in a variable). Start command cache-only: `redis-server --requirepass $REDIS_PASSWORD --maxmemory 512mb --maxmemory-policy allkeys-lru --save '' --appendonly no` (the template ships `--save 60 1` and no `maxmemory`). Web variable `REDIS_URL=${{redis.REDIS_URL}}` (host must be `redis.railway.internal`); changing a web variable redeploys, so run the web source check first and use `railway redeploy` of the tagged release. Check from `railway ssh`: `getent hosts redis.railway.internal`. Cost [U, quoted prices]: about $1-6/month (0.6 GB x $10 per GB-month at full; cents idle), no egress on the private network. Working set is small: 20 metros 84.8 MB with both encodings, facets 1.0 MB, aggregates 0.49 MB; 512 MB holds about 54 Orange-County-sized bodies or 260 Charlotte-sized ones.

**What the staged releases already change.** `redis>=8.0.1` and `brotli>=1.1` are already in `requirements-web.txt` (lines 23 and 36; no new dependency; `psycopg-pool` is NOT listed). 1.5.16 (N37.11) removed the SQLite fallback, so the limiter is in-process only: with N workers every limit is N times larger and every deploy resets login lockout and the 24-hour AI budgets (the reason R2 precedes more workers). 1.5.11 limits facet rebuilds to one per 300 s and moves the 125-210 s registry backfill into a startup thread (still one UPDATE per worker per restart; add `pg_try_advisory_lock` only with more workers). 1.5.12 adds the 20-per-minute cache-miss build limiter (in process, times N). `CARD_REV` changes at 1.5.11, 1.5.12 and 1.5.16, so stored bodies are invalid at each of those deploys anyway (facets keyed by fingerprint alone survive). Not changed: ETag/gzip header (`listings_api.py:322-324`), the TTL loaders, the connection path, worker flags.
